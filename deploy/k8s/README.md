# Ledgerline on Kubernetes

The production topology: one Deployment per service (gateway ×2, payments ×2, fraud ×2, ledger ×1), PostgreSQL with
one database per service, RabbitMQ and Keycloak — in a namespace that enforces the `restricted` Pod Security Standard,
behind default-deny NetworkPolicies where only the gateway accepts traffic from outside.

```bash
./deploy/k8s/kind.sh      # builds the images, deploys on a local kind cluster, smoke-tests through the gateway
```

CI runs the same script on every push, then the Playwright suite against the cluster.

| Concern | How |
|---|---|
| Secrets | Generated by `kind.sh` into the `ledgerline-secrets` Secret, injected as env vars and composed into connection strings with `$(VAR)` expansion: no secret in a manifest. |
| Start order | None needed. Services wait for PostgreSQL (`DatabaseReadiness`), subscribers request the account directory on startup (`RequestAccountDirectory`), outboxes retry until RabbitMQ is up. |
| Probes | `startupProbe`/`livenessProbe` on `/alive` (process), `readinessProbe` on `/health` (dependencies). |
| Hardening | Chiseled non-root images, read-only root filesystem, all capabilities dropped, seccomp `RuntimeDefault`. |
| Ledger replicas | One, because it runs the demo seeder. The services are otherwise stateless: concurrency is handled by optimistic stream versions, not by a single writer. |

Keycloak runs in dev mode with the realm imported at start, and PostgreSQL/RabbitMQ as single pods: that is the demo
part. In production they would be a managed PostgreSQL, a RabbitMQ cluster (or operator) and a Keycloak backed by its
own database.
